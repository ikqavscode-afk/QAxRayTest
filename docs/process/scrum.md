# Процесс разработки: Agile / Scrum

Проект ведётся короткими итерациями (спринтами). Каждая итерация даёт работающий,
проверенный автотестами и опубликованный прирост продукта.

## Роли

| Роль | Кто |
|---|---|
| Владелец продукта | Автор проекта: приоритеты, приёмка, ответственность за бэклог |
| Разработчики | Автор проекта: оценка, реализация, тесты |
| Ведущий процесса | Автор проекта: соблюдение ритуалов и определений готовности |

Одна и та же команда из одного человека не отменяет ритуалы: каждый ритуал оставляет
письменный след в репозитории.

## Артефакты

| Артефакт | Где лежит |
|---|---|
| Продуктовый бэклог | [docs/backlog/product-backlog.md](../backlog/product-backlog.md) |
| План спринта (цель, выбранные задачи, критерии, риски) | `docs/sprints/sprint-NN-plan.md` |
| Прирост продукта | код, тесты, документация в `main`, зелёный CI |
| Итоги и ретроспектива | `docs/sprints/sprint-NN-retrospective.md` |
| Архитектурные решения | `docs/decisions/NNNN-*.md` |

## Ритуалы и цикл спринта

1. **Уточнение бэклога** (в конце каждого спринта и по мере необходимости): задачи
   переупорядочиваются по ценности и риску, большие делятся до размера не более 8 очков,
   у задач появляются критерии приёмки.
2. **Планирование спринта**: формулируется цель, из верха бэклога берутся задачи в пределах
   скорости команды (среднее выполненное за прошлые спринты). Результат: файл `sprint-NN-plan.md`.
3. **Работа по задачам**: цикл TDD (тест, красный результат, код, зелёный результат),
   небольшие коммиты, полная цепочка проверок перед каждым коммитом.
4. **Ежедневная сверка** (даже если работа в одиночку): что сделано, что дальше, что мешает.
   Заметка в чате или журнале, при необходимости изменения вносятся в план спринта.
5. **Обзор спринта**: показ прироста вживую (консоль, веб-форма, живая матрица целей),
   сверка с целью спринта и критериями приёмки, обновление бэклога по итогам.
6. **Ретроспектива**: что получилось, что мешало, уроки, технический долг, улучшения процесса.
   Результат: файл `sprint-NN-retrospective.md`.

Длина спринта задаётся объёмом (около 25–30 очков), а не календарём. Когда появится постоянный
график работы, длина фиксируется в днях.

## Оценка и скорость

- Оценка в очках по шкале Фибоначчи (1, 2, 3, 5, 8). Задача больше 8 очков делится.
- Скорость: сумма очков задач, принятых в спринте. Планирование берёт среднее последних спринтов.
- Очки прошлых спринтов выставлены задним числом и приблизительны; со Sprint 3 оценка
  делается до начала работы и сверяется с результатом на ретроспективе.

## Приоритеты

MoSCoW: **Must** (без этого MVP не выпускается), **Should** (нужно, но MVP переживёт задержку),
**Could** (по возможности), **Won't** (вне MVP).

## Определение готовности задачи (Definition of Ready)

- Есть история пользователя или формулировка цели и критерии приёмки.
- Оценка не больше 8 очков, зависимости известны.
- Продуманы риски безопасности: нет новых запросов без лимитов и политики адресов.
- Понятно, как проверить результат автотестом (и вживую, если применимо).

## Определение завершённости (Definition of Done)

Задача завершена, только если выполнено всё:

1. Сначала написан тест и получен красный результат; затем код и зелёный результат.
2. Проходит полная цепочка: форматирование, тесты, линтер, типы (`mypy --strict`), проверка контента.
3. Обновлены README и документация; важные решения записаны в ADR.
4. Безопасность: лимиты и тайм-ауты, политика адресов, нет секретов в отчётах и логах.
5. Если задача меняет поведение для пользователя, она проверена вживую на безопасной цели.
6. Коммит с понятным сообщением; CI на `main` зелёный.
7. Проверка контента не находит запрещённых упоминаний и личных данных.
8. Для изменений интерфейса: проходят стражи `test_ui_standards.py`, интерфейс проверен в браузере
   на 375 и 1280 px (нет горизонтального переполнения, цели не меньше 44 px), основной сценарий
   проходится только клавиатурой ([стандарты](../standards/ui-ux-standards.md)).
