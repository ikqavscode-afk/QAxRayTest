# ADR-0005. Проверки API и чтение описания

Статус: принято. Дата: 2026-11-07.

## Контекст

Нужны проверки API (группа E) без риска изменить данные или нагрузить чужой сервис.
Неизвестно, какие методы безопасны, поэтому приложение не должно угадывать.

## Решение

1. **Только `GET` и только пути пользователя** (до 10). Пути из документации автоматически
   не подставляются. Путь начинается с одного `/`, не содержит пробелов, `..`, схемы и `//`,
   поэтому не может сменить хост. Адрес документации и базовый адрес API проходят ту же
   политику безопасности, что и адрес сайта, а запросы идут через тот же клиент.
2. **Каждый адрес запрашивается один раз** (кэш в контексте), включая сбои.
3. **Ожидаемый статус**: по умолчанию 200; для пути можно задать список (`/ping | 201`,
   `--api-expect /ping=201`), не более 5 статусов в диапазоне 100–599.
4. **Эвристики** (QC-022, QC-024) дают `PASSED` или `WARNING`; находка о контракте не объявляется
   `FAILED`, пока схема читается упрощённо.
5. **Чтение описания (QC-024)**: OpenAPI 3.x и Swagger 2.0 только в JSON; локальные `$ref`,
   `allOf`, массивы (первые 20 элементов), пути с параметрами, префикс сервера. Внешние `$ref` не
   загружаются, циклы не зацикливают. Нет схемы, YAML или документация больше лимита чтения:
   `SKIPPED` с причиной.
6. **Отчёт без секретов**: параметры запроса из путей не попадают в отчёт и доказательства;
   тела ответов в отчёт не включаются.

## Последствия

- Сетевой сбой на одном пути блокирует проверки по путям целиком (результат по каждому пути
  отдельно: задача на будущее).
- Приложение не заменяет контрактное тестирование: оно проверяет базовое поведение и сигнализирует.
- Реальные адреса для проверки хранятся вне репозитория (см. раздел о живых тестах в README).
