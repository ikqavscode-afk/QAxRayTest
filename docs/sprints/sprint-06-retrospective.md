## Обзор спринта (демонстрация)

- Форма и остановка принимают только запросы с токеном сессии и с верным `Origin`; запрос без токена получает 403.
- Один адрес клиента может запускать не более 10 проверок за минуту; третий запуск при лимите 2 получает 429 с
  `Retry-After`; подделка `X-Forwarded-For` лимит не обходит.
- HTTP-клиент соединяется только с IP, проверенным политикой; подмена DNS между проверкой и соединением отклоняется
  без открытия сокета; HTTPS работает (SNI и сертификат по имени), настоящий `example.com` отвечает 200.
- Аудит интерфейса на 9 страницах и ширинах 1280, 375 и 320 px: два нарушения зон нажатия 44 px исправлены.
- Настоящий запуск `example.com` (11 PASSED, 1 WARNING, 13 SKIPPED) и Petstore с API (16 PASSED, 2 WARNING); веб-форма
  с Chrome и скачивание архива Allure проходят.
- Опубликован релиз `v0.1.0` с описанием из [CHANGELOG.md](../../CHANGELOG.md).

## Что прошло хорошо

- Все 19 SP, CI зелёный на каждом опубликованном коммите, релиз с первой попытки.
- Каждую защиту проверяли дважды: тестом и настоящим поведением (браузер, настоящее соединение, настоящий сайт).
- Пуши и релиз подтверждались сверкой `HEAD`, `origin/main` и тега, а не словами.
- Решения оформлялись ADR прямо в задаче; ADR-0003 с рисками обновлён и больше не врёт.
- Раздел «Публикация и ограничения» в README честно перечисляет, чего версия не умеет.

## Что мешало

- Скринридер недоступен в моём окружении: PB-053 закрыт замерами и деревом доступности, а не прослушиванием.
  Остаётся задача владельцу.
- Лишняя настройка без отдельного согласования: `QAXRAY_COOKIE_SECURE` добавлена в PB-054 ради обещания из ADR-0013.
  Она только усиливает защиту и по умолчанию выключена, но правило «настройки не расширять без подтверждения»
  требовало спросить заранее.
- Демо-сервер показал старый шаблон после правки (шаблон Flask кэшируется): сначала я принял устаревшую страницу за
  результат правки. Урок: после правки шаблона перезапускать сервер, прежде чем делать выводы.
- Один раз перепутал идентификатор запуска при ручной проверке (404), заметил по заголовку страницы.
- Часть новых тестов писалась после кода, а красный результат был «модуль не найден», а не поведение.

## Уроки

1. Защиту проверять и тестом, и реальным поведением: настоящее соединение с локальным сервером и живой запрос на
   `example.com` нашли бы то, что заглушки пропускают.
2. Новую настройку согласовывать до реализации, даже если она «только усиливает».
3. Ручную проверку после правки шаблона начинать с перезапуска сервера.
4. Задачи, которые нельзя выполнить полностью (скринридер), записывать как остаток для владельца явно, а не закрывать
   молча.
5. Релиз подтверждать сверкой `HEAD`, `origin/main`, тега и CI.

## Технический долг и риски

- Интерфейс не прослушан скринридером (VoiceOver, NVDA); состояния `hover` и `disabled` (PB-067).
- Отчёты в памяти (1 час), один процесс; постоянное хранение, краткая и полная версия отчёта, учёт запусков и выгрузка
  для владельца обсуждены, решения нет, в бэклог не внесено.
- За обратным прокси ограничение частоты не различает клиентов; публичная демо требует решения о ключе клиента.
- Версия Chrome в bug report не записывается; остановка не прерывает идущий HTTP-запрос (PB-069); недоступный сайт
  отвечает около 50 секунд (PB-068); документация API в YAML не читается (PB-060).
- Браузерные тесты на настоящем Chrome в CI идут отдельным заданием и сработают только при изменении браузерного кода
  или по расписанию.
